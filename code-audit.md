## Executive summary

The codebase is broadly functional but carries a recurring set of structural weaknesses concentrated in three themes: **silent failure modes** (actions that report success when nothing happened, or fail with no signal), **non-atomic read-then-write operations** against the local SQLite store (cancel/update/draft/dedupe paths that race the scheduled-send promoter or each other), and **unguarded I/O and JSON parsing** that can take down a request — or the whole runner — on a single bad input. The single most dangerous finding is an unlistened read-stream in the iMessage attachment server that escalates to `process.exit(1)`, downing every platform; close behind are destructive maintenance scripts (dedupe/reset/purge) that merge or wipe records irreversibly with no dry-run and weak identity checks. The user's headline concern — **UI feedback gaps** — is pervasive: many operator actions (menu items, demo start, name edits, scan, open-in-platform) fire async runner calls with no pending state, no success confirmation, and in several cases swallowed or mis-attributed errors. Send-verification defects on the LinkedIn and Beta adapters can record a message as *sent* when it never left the browser, which is the most consequential correctness risk for the product's core promise. Most Medium/Low items are recoverable or latent, but they compound: the same missing-guard patterns recur across scripts, services, and routes, so fixing the shared helpers (atomic conditional updates, `runActionWithFeedback`, `safeJsonParse`, dry-run flags) retires many findings at once.

## Critical & High findings

### [CRITICAL] pipeFile streams file to response with no error handler — read error crashes the runner
File: `apps/runner/src/services/imessage-attachment-server.ts:80-87`
Category: error-handling
What's wrong: `pipeFile` does `createReadStream(path).pipe(res)` with no `.on("error")` listener and no `res.on("close")` cleanup. It returns void synchronously after registering `.pipe()`, so `streamIMessageAttachment`'s promise resolves before any stream `'error'` fires; `asyncRoute`'s `void handler(...).catch(next)` cannot intercept the async stream error, so an unlistened ReadStream `'error'` becomes an uncaught exception.
Why it matters: `process.on("uncaughtException")` (index.ts:4154) logs and then calls `process.exit(1)` (line 4168). A read failure mid-stream (file unlinked/permission-revoked between `statSync` and the read, Messages.app attachment cleanup, OS upgrade) deliberately kills the entire Express+Playwright runner, downing all platforms. The fix that adds this guard exists in commit d03a4a1/5d425f3 but is not an ancestor of HEAD.
Fix: Port the guard from d03a4a1: register `stream.on('error', err => { if (!res.headersSent) res.status(500).json({error:'stream read failed'}); else try { res.destroy(err); } catch {} })` and `res.on('close', () => { if (!stream.destroyed) stream.destroy(); })` before calling `stream.pipe(res)`.

### [CRITICAL] Dedupe merges distinct humans by displayName label alone, cross-contaminating threads and deleting Person rows
File: `apps/runner/src/scripts/dedupe-imessage-people.ts:24-58`
Category: data-integrity
What's wrong: `main()` selects only id/displayName/createdAt/notes (not handle) and groups purely on `p.displayName.trim().toLowerCase()`. For every group of 2+ it re-parents all duplicates' threads onto the canonical and `prisma.person.delete()`s the duplicate with no identity check. The adapter produces non-unique displayNames (1:1 chats fall back to the raw chatIdentifier; groups comma-join per-participant handles with raw fallback). `Person.handle` exists in the schema (line 85) but is never compared.
Why it matters: Two genuinely distinct identities that share a label (two unresolved phone strings, two real "John Smith" contacts, two groups with the same unresolved participant set) get merged — identity B's threads move under A and B's row is destroyed. Irreversible cross-contamination plus record loss on the exact path the script walks.
Fix: Match on a stable identity, not the label. Persist/compare `Person.handle` and merge only rows whose normalized handle/phone matches (use `siblingHandles(handle)` at contact-resolver.ts:155 to group multiple numbers of one contact). Skip any group whose key is empty/blank or still phone-shaped, and default to a dry-run behind an explicit `--apply` flag.

### [HIGH] Scheduling a send silently drops staged composer attachments
File: `apps/dashboard/app/thread/[id]/page.tsx:1180-1205, 3515-3576`
Category: data-integrity
What's wrong: `scheduleSend` posts only `{ text, clientSendId, scheduledFor }` via JSON `apiPost`; it never reads or appends `composerAttachments`. The immediate `onSend` path detects `attachmentsToSend.length > 0` and uploads them via FormData, proving the multipart capability exists and is only wired into the immediate path. The schedule button gates only on `composer.trim()/sending/scheduling`, never on attachments, and on success clears `setComposer("")` but never `composerAttachments`.
Why it matters: An operator stages photos/files + text, schedules, and the later-fired message carries text but no attachments, with zero warning — genuine silent content loss on a path the operator believes succeeded. iMessage attachments are real (file input gated on `thread.platform === 'IMESSAGE'`).
Fix: In `scheduleSend`, when `composerAttachments.length > 0` build a FormData (mirroring onSend at 947-959) including each `a.file` and `scheduledFor`, then clear attachments and revoke preview URLs on success. If the scheduled-send endpoint cannot persist attachments yet, instead disable the schedule button when attachments are staged with a tooltip and surface a note — never drop them silently.

### [HIGH] Menu actions (Reconnect / Run selector tests / Reset session) use runAction — no pending state, silent on success
File: `apps/dashboard/app/platforms/page.tsx:182-216`
Category: ui-feedback-gap
What's wrong: Reconnect (182-187), Run selector tests (193-198) and Reset session… (211-215) all call `runAction(...)`, not `runActionWithFeedback`. `runAction`'s success branch only does `setError(null)` — no toast, no pending UI. The Menu closes immediately on select, so no control survives to flip and there is zero success signal. The runner endpoints are genuinely slow (reset-session acquires a global lock and awaits every platform mutex; test-selectors and connect run under platform control locks).
Why it matters: Three operator actions, including a destructive global reset, give no in-flight or success feedback — only a shared `actionError` string at the top of the page. Directly violates the product's every-action-surfaces-feedback bar.
Fix: Route all three through `runActionWithFeedback` like the sibling "Scan now". Reconnect: `{ pending: 'Reconnecting …', success: '… reconnected', failure: "Couldn't reconnect …", setError: setActionError, onDone: () => refresh() }`; mirror for Run selector tests and the destructive Reset session.

### [HIGH] Name confirm/rename/dismiss has no error feedback and leaks an unhandled rejection on failure
File: `apps/dashboard/components/common/name-suggestion-pill.tsx:59-69`
Category: ui-feedback-gap
What's wrong: `call()` awaits `apiPost` inside try/finally with no catch. `apiPost` throws `ApiRequestError` on any non-ok response and rejects when the runner is offline. On rejection the finally clears `busy`, the success branch is skipped (popover stays open unchanged), and the rejection propagates out — every caller invokes it as `void call({...})`, making it an unhandled promise rejection. The component imports only `apiPost`, holds no error state, and has no catch, so there is zero user-visible error signal.
Why it matters: A name confirm/rename/dismiss that fails leaves the operator with no signal and floats an unhandled rejection. Violates the product's error-signal bar.
Fix: Route through `runActionWithFeedback(apiPost(...rename), { pending: 'Updating name…', success: 'Name updated', failure: "Couldn't update name", onDone: () => { setOpen(false); setEditing(false); onChanged(); } })` so the popover only closes on success. At minimum add a `.catch` that surfaces `showToast({ kind: 'error' })` and keeps the popover open.

### [HIGH] Send verification falsely reports success via timestamp_advanced when no message bubble was actually sent
File: `apps/runner/src/platforms/linkedin-adapter.ts:9203-9211, 9286-9304`
Category: data-integrity
What's wrong: `getLatestMessageSnapshot` reads the last bubble's `<time>`, `Date.parse()`s it, and on NaN substitutes `Date.now()`. LinkedIn drops `datetime` on most prod renders (times like "4:52 PM" parse to NaN), so the NaN→`Date.now()` path is the common case. The verify loop's only signals are the last bubble's direction + timestamp; `timestampAdvanced = !preSend || last.timestamp > preSend.timestamp` is essentially always true from read-time clock drift when both snapshots synthesize `Date.now()`. When the most recent bubble is already OUT (operator re-replying) and the new send silently fails, `last.direction==="OUT" && timestampAdvanced` fires and returns `verifiedBy='timestamp_advanced'`.
Why it matters: Downstream `send.ts` treats any returned receipt as success — upserts the OUT message, sets `lastOutboundAt`/`unreadCount:0`, sets `status='SENT'`, emits `MESSAGE_SENT` — without inspecting `verifiedBy`. A silently-failed LinkedIn send is recorded and surfaced as sent.
Fix: Disable the `timestamp_advanced` path when the timestamp was synthesized — have `getLatestMessageSnapshot` return `timestampSynthetic` and require `textMatch` (bubble_detected) when true. Better: capture the OUT bubble count and/or last bubble's stable `platformMessageKey` (data-event-urn) pre-send and only accept success when the count increases or a new matching OUT bubble appears.

### [HIGH] Beta send returns a success receipt even when the send-button click failed and Enter was a no-op
File: `apps/runner/src/platforms/beta-adapter.ts:402-409`
Category: data-integrity
What's wrong: In `sendMessage` the send-button click is `...click({ timeout: 10000 }).catch(async () => { await page.keyboard.press("Enter"); })` followed by an unconditional `return { sentAt, verifiedBy: "best_effort" }` — no post-send verification. By contrast the LinkedIn adapter does a bare `.click()` that throws on failure, then runs a real 10s verify loop.
Why it matters: `send.ts` takes any returned receipt, upserts the OUT message, updates the thread, sets `status="SENT"`, and emits `MESSAGE_SENT`, independent of `verifiedBy` — so `"best_effort"` is treated as terminal exactly like `"bubble_detected"`. If the selector drifted (click times out) and Enter doesn't dispatch on the IG/TikTok composer (newline / not focused), the user is told the reply was sent when it never left the browser.
Fix: Mirror the LinkedIn adapter: capture a pre-send snapshot, do not swallow the click, then poll for a new matching OUT bubble and/or advanced timestamp. Only return a receipt when verification passes; otherwise throw an `AdapterFailure` (THREAD_FETCH_FAILED/SELECTOR_MISMATCH) so `send.ts` records FAILED and the dashboard shows an error + retry.

### [HIGH] cancelScheduledSend reads-then-writes without a status guard — can mark an already-sent message CANCELLED
File: `apps/runner/src/services/send.ts:540-560`
Category: race-condition
What's wrong: `cancelScheduledSend` does `await prisma.sendRequest.findUnique` (yields the event loop), checks `row.status === 'SCHEDULED'`, then issues an unconditional `update` keyed only on `clientSendId` setting `status:CANCELLED`. The route handler (index.ts:1682) uses no mutex/transaction. The scheduled-send promoter runs on its own `setInterval` and is not serialized against this handler; its tick can dispatch during the awaited `findUnique`, promote the row (SCHEDULED→PENDING), and the queue worker can drive `processSendRequest` to the adapter. `processSendRequest` reads status once and never re-checks, so a late CANCELLED write does not stop the in-flight send.
Why it matters: The message is actually delivered but the row terminal-states as CANCELLED and the operator is told "cancelled" — corrupted terminal state plus a false outcome on a real outbound message.
Fix: Make cancel atomic and conditional: `const r = await prisma.sendRequest.updateMany({ where: { clientSendId, status: 'SCHEDULED' }, data: { status: 'CANCELLED' } })` and treat `r.count === 0` as losing the race (`return { cancelled: false, reason: 'no_longer_scheduled' }`). The SQL-level WHERE closes the promoter interleave.

### [HIGH] runOnce() drives the shared LinkedIn page without the enrich lock, racing a concurrent background drain
File: `apps/runner/src/services/enrichment-queue.ts:357-381`
Category: race-condition
What's wrong: `processJob` acquires the enrich lock around the profile visit (`tryAcquire(deps.enrichLockKey, () => visitProfile(...))`). `runOnce` calls `visitProfile(personId)` directly with no enrich-lock acquisition; its only guard checks `operationMutex.isRunning` for scan/send keys, not the enrich key. `getManagedPage` returns the cached per-platform Page, so `processJob`'s in-flight `extractProfile` and a `runOnce` fired by the manual-refresh `?wait=1` endpoint (index.ts:3302) drive the same Chrome page concurrently.
Why it matters: One call's `page.goto` can interrupt the other's DOM extraction ("Execution context was destroyed") or cross-contaminate the persisted profile. The lock key is a single fixed constant, so this is a true unguarded shared-resource race.
Fix: Acquire the enrich lock in `runOnce` just like `processJob`: `const acquired = await deps.operationMutex.tryAcquire(deps.enrichLockKey, () => visitProfile(personId)); if (!acquired.acquired) return { deferred: true };` then proceed with the existing branches.

### [HIGH] Duplicate Person notes are silently lost when the canonical row already has notes
File: `apps/runner/src/scripts/dedupe-imessage-people.ts:46-54`
Category: data-integrity
What's wrong: Line 46 copies the duplicate's notes onto the canonical only `if (!canonical.notes && dup.notes)`. When the canonical already carries notes, that branch is skipped and the duplicate is deleted at line 54 with no merge, append, log, or warning.
Why it matters: Any operator-written notes on the duplicate are permanently and irreversibly discarded. Bounded by how often both rows carry notes, but it is operator-authored content.
Fix: When both rows have non-empty notes, concatenate the duplicate's onto the canonical with a dated divider instead of dropping them; at minimum log a loud warning printing the duplicate id and its notes before deleting so the operator can recover them.

### [HIGH] Unrecognized --platform silently falls back to wiping LINKEDIN
File: `apps/runner/src/scripts/reset-linkedin-inbox.ts:19-42`
Category: data-integrity
What's wrong: `options.platform` defaults to `"LINKEDIN"`. The `--platform` branch only reassigns when the uppercased value exactly equals LINKEDIN/INSTAGRAM/TIKTOK/IMESSAGE; on any other value (typo, "insta", "LINKDIN") the if is false, the index still advances, and the loop continues with the LINKEDIN default. There is no "unrecognized platform" branch or abort. `run()` then calls `resetPlatformInboxGraph(options.platform)`, which deletes all sendRequests/drafts/messages/threads for that platform plus orphaned Person rows. `validateAdminResetGuards` only checks the env token and `confirm==='RESET'`, never the platform.
Why it matters: An operator who fat-fingers `--platform` while supplying a valid token + RESET silently wipes the entire LinkedIn graph instead of the intended platform. The canned `db:reset:linkedin` hardcodes `--platform LINKEDIN`, so this fail-open only bites a manual invocation — but within expected operator conditions it is a silent, irreversible mass-delete of the most-populated platform.
Fix: Track whether `--platform` was supplied and validate its value: if present but not one of the four, throw/exit non-zero with `Unrecognized platform: <value>`. Ideally make `--platform` required (no implicit default) for a destructive wipe so a missing/typo'd flag aborts.

3. **Send-verification false positives (HIGH, linkedin-adapter.ts:9203-9211/9286-9304 and beta-adapter.ts:402-409).** Recording a send as successful when nothing left the browser undermines the product's core promise. Require a real bubble-count/key delta or text match before returning a receipt.

Mostly mechanical, and it also fixes the unhandled rejection in the name pill and the stale shared `actionError`.
7. **The shared unguarded-parse / runner-resilience cluster (Medium).** `getSettings` JSON guard, `event-bus` per-listener try/catch, `/data/thread` `safeJsonParse`, and the AI client timeout — each one removes a single-point-of-failure that can wedge or down the runner, and they reuse helpers that already exist in the codebase.
